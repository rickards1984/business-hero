Read-only design review completed on `ticket/OUT-23-hunter`. Nothing modified, committed or pushed; tests not run.

1. **P1 — B-2/B-7: “Found published” needs a stricter acceptance contract.**  
   `still_on_page=true` alone has no freshness requirement in the design. An old directory entry can therefore qualify without establishing current publication. Hunter now exposes `provenance`, including `found`, `inferred` and a forthcoming `previously_found`; the proposed request and acceptance rules ignore it. **Fix:** request `provenance=found`, require that returned provenance explicitly, reject unknown values, and define acceptable source age using `last_seen_on`. If current publication is required, fetch the selected page safely and check the complete address. A third-party directory can establish publication, but does not establish company ownership or permission to market. Test stale, contradictory and malformed source records. [Hunter API reference](https://hunter.io/api-documentation/v2#domain-search)

2. **P1 — B-2/B-7: The verification-to-storage contract can manufacture fresh validity.**  
   Today’s [`_store`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_research.py:778) writes `verification_status="valid"` and `verified_at=moment` for every eligible contact. “Store it as today” plus a textual `hunter:valid` fact does not specify how Hunter’s actual verification date, address binding and expiry replace those defaults. An 89-day-old result could become freshly verified evidence. The design also lists `webmail` and `disposable` alongside statuses without defining their separate boolean checks. **Fix:** specify typed, fail-closed validation, exact returned-email matching, non-future dates, explicit boolean exclusions, and the actual verification timestamp and expiry. Failed Hunter results must never fall through to web verification or review storage. Add database-grounding tests and a real prepare/claim test, including missing dates, future dates, mismatched addresses and contradictory flags.

3. **P1 — B-2 steps 4–5: Free rejection checks follow paid verification.**  
   A suppressed email, recently erased person or domain without mail service can incur Verifier charges before step 5 rejects it. Up to ten results could be verified before selecting one. **Fix:** check domain MX before Domain Search; after its response, apply source, address, suppression, erasure and contact-type quota checks before verification. Rank survivors first and verify sequentially, stopping at the first usable person. Test that an email-only suppression causes zero Verifier calls and that lower-ranked people are not verified after success.

4. **P1 — B-2/B-5/B-7: The paid-call reservation and concurrency protocol is incomplete.**  
   The existing loop verifies an entire batch before storing it. Its [`_claim_search`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_research.py:739) lease lasts 15 minutes; Hunter searches and polling can outlast that. Two candidates for the same domain can also spend credits before either is stored. A gate checking only “cap not reached” permits a one-credit call with half a credit remaining.  
   **Fix:** define committed maximum-cost reservations before every billable operation, settlement independent of prospect storage, conservative accounting for timeouts/crashes, and lease renewal/ownership checks before calls and storage. Track pending domains and remaining slots within the run; recheck live authority, cap and room. Specify a total call/time budget including polling, not just `2 × room` searches. B-7 needs PostgreSQL interleavings, lease takeover, disconnect/pause during a call, repeated domains, crash-after-charge and insufficient-remainder tests.

5. **P1 — B-5/B-8: The proposed secret location is returned by existing settings endpoints.**  
   [`GET /v1/business/settings`](/Users/michaelrickards/dev/bh2-HUNTER/backend/main.py:1467) and the PUT response return the full settings document. Putting `key_ciphertext` there exposes it to the browser, contrary to B-5. Encryption prevents plaintext disclosure but does not satisfy the stated boundary.  
   **Fix:** redact server secrets from every settings response or use server-only storage. Preserve the existing protection against generic PUT overwrites. Define owner-only connect/disconnect, tenant checks, and a connection generation so an old request cannot restore state after disconnect or key replacement. `X-API-KEY` is supported, but require header redaction, no query-string fallback, no credential-bearing redirects, and sanitised exceptions. Test generic GET/PUT, failure logs, missing encryption configuration and disconnect races. [Hunter authentication](https://hunter.io/api-documentation/v2#authentication)

6. **P1 — B-5/B-7: Metering does not define fractional units or quota state correctly.**  
   Existing [`_add_meter`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_research.py:410) casts increments to integers: reuse would record a 0.5-credit verification as zero. Hunter also exposes `X-Credits-Unit` and supports both unified credits and separate search/verification quotas. A single unqualified total is insufficient. **Fix:** define exact storage units, supported account models and explicit handling of missing/malformed cost headers. Persist quota blocks independently of the hourly cache; define reset-date timezone, missing/past reset dates and refresh failure. Invalidate cache on connection changes, cache only required account fields, and label cached balances with their timestamp. Test zero-cost repeats, fractional charges, separate pools, month versus billing-period boundaries, and a stale cache after 429. The documented 401/403/429 mapping itself is correct. [Hunter account and cost documentation](https://hunter.io/api-documentation/v2#account)

7. **P1 — B-3/B-7: “The same evidence row” does not reliably identify acquisition provenance.**  
   [`build_payload`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_send.py:214) selects the newest evidence row with any source URL, without a fact-type restriction or deterministic tie-breaker. A later web fact can remove Hunter attribution; mixed source pages can select something other than the page publishing the address. The hash faithfully binds that wrong footer.  
   **Fix:** define an authoritative acquisition-source record and deterministic selection. Its URL must be the chosen address-publication page, even when that is a directory; company-registration evidence belongs separately. Preserve already-approved payloads and claimed jobs unchanged. Test mixed/tied evidence, later verification, old web cards, manual and automatic claims, and dispatch of an already-claimed payload. A conditional footer change alone need not invalidate existing cards.

8. **P1 — B-4/B-7: A timestamp does not bind confirmation to the notice or assessment actually used.**  
   An owner can confirm Hunter wording, then replace the published notice through [`approve_privacy_notice`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_setup.py:1008); `notice_confirmed_at` would remain valid. Existing audience approval also need not assess database/directory sourcing. Naming Hunter is appropriate attribution, but neither publication nor corporate status supplies the lawful basis by itself.  
   **Fix:** bind confirmation to brand, approving owner and published notice version/hash; require re-confirmation when that version changes, and ensure the approved assessment covers the new sourcing. Check this before acquisition and first send. The notice must provide the applicable Article 14 information, including actual source/public availability, rather than just add a category. Retain corporate-subscriber checks, identity and opt-out. ICO guidance requires a legitimate-interests assessment and timely privacy information for indirectly collected business contacts. [ICO B2B guidance](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/business-to-business-marketing/)

9. **P2 — B-2: Home-page-only corporate verification is not equivalent to today’s check.**  
   Today’s [`_verify`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_research.py:518) checks the cited company page, validates its final host, and can obtain registration or trading-name evidence there before falling back to the home page. A legitimate company disclosing registration only on its contact page now fails. The abbreviated replacement also leaves redirect ownership and designer-credit exclusions unspecified.  
   **Fix:** extract and reuse the existing corporate predicate, allowing a cited company-owned legal/contact page and a home-page fallback. Keep publication evidence separate when Hunter’s source is external. Require the same visible registration/name binding, final-host checks and exclusions. Test contact-page-only disclosures, off-domain redirects, designer registrations and trading names.

10. **P1 — B-5/B-7: A 451 rejection can be bypassed by another acquisition path.**  
    “Skip that person and store nothing” lets a later ordinary web candidate acquire the same address, because B-2 leaves that path unchanged. Hunter explicitly describes `claimed_email` as a request to stop processing that person’s data. **Fix:** define a minimal tenant-scoped exclusion consistent with existing suppression handling, apply it to all acquisition paths, and prevent fallback after 451. Do not store the rejected profile. Test Hunter rejection followed by web rediscovery and a concurrent pending candidate. [Hunter Verifier errors](https://hunter.io/api-documentation/v2#email-verifier)

11. **P2 — B-5/B-7/B-8: Erasure coverage is asserted more broadly than the existing implementation provides.**  
    [`outreach_erasure`](/Users/michaelrickards/dev/bh2-HUNTER/backend/services/outreach_erasure.py:318) deletes never-contacted prospects and their evidence; it deliberately retains contacted cases. Raw account-cache responses, diagnostic payloads or new retry records would fall outside that deletion graph. **Fix:** specify an allowlist for every persisted Hunter field, prohibit raw response/profile logging, keep learning facts in prospect-linked evidence, and make meters aggregate-only. Document contacted-subject/provider-copy handling as the existing OUT-13 dependency rather than imply it is solved. Add erasure tests covering source URLs, verification facts, learning facts, cards, summaries and any new cache/retry state.
